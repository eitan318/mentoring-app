🗺 How Navigation Works — NavigationService & Store

MentoringApp — a clear, visual walkthrough of the custom MVVM navigation system

💡 The Big Picture — Why a custom navigation system?

WPF has a built-in Frame + Page navigation system, but it's tightly coupled to WPF. Because this project shares the same ViewModel layer between WPF and Blazor Web, we can't use anything WPF-specific.

Instead, navigation is handled entirely in the ViewModel layer — the View just listens to a property and displays whatever ViewModel is active. This means the same navigation logic works in both WPF and Blazor.

📺 Real-world analogy

Think of a TV with one screen. A remote control changes what's on the screen by updating a "channel" variable. The TV doesn't know what channel 5 shows — it just displays whatever it's told. The remote keeps a history so you can press Back to return to the previous channel.

💻 In code

The ContentControl in MainWindow is the TV screen — it binds to CurrentViewModel and displays whatever ViewModel is set. The NavigationService is the remote — it changes CurrentViewModel. The NavigationStore keeps the back-stack history.
🧩 The Three Moving Pieces
1. NavigationStore
Holds the current ViewModel and a back-stack (a Stack<>). When CurrentViewModel is set, the previous one is pushed onto the history stack. Fires an event when it changes.
2. NavigationService
The public API that all ViewModels call. It creates ViewModels (via DI), tells the Store to switch, and manages nested contexts — one stack of stores, one per shell level.
3. ContentControl + DataTemplates
The View is totally passive. ContentControl binds to the active ViewModel, and WPF automatically picks the matching View from ViewModelViewMap.xaml — no code-behind switch needed.
1 NavigationStore — the back-stack in detail

The store is a private class inside NavigationService. It holds a Stack of previously visited ViewModels and the current one.

// Simplified from NavigationService.cs
private class NavigationStore
{
    private readonly Stack<INavigatable> _navigationHistory = new();
    private INavigatable _currentViewModel;

    public bool CanGoBack() => _navigationHistory.Count > 0;

    public INavigatable CurrentViewModel
    {
        get => _currentViewModel;
        set
        {
            // Push current to history before switching
            _navigationHistory.Push(_currentViewModel);
            _currentViewModel = value;
            CurrentViewModelChanged?.Invoke(); // ← notifies the UI
        }
    }

    public void GoBack()
    {
        _currentViewModel = _navigationHistory.Pop(); // restore previous
        CurrentViewModelChanged?.Invoke();
    }

    public void ResetTo(INavigatable vm)
    {
        _navigationHistory.Clear(); // wipe history (no back button)
        _currentViewModel = vm;
        CurrentViewModelChanged?.Invoke();
    }

    public event Action? CurrentViewModelChanged;
}

2 Nested Contexts — why there are two levels of navigation

The app has two independent navigation areas that must not interfere with each other:

  • Outer context — the main window. Shows Login → Dashboard shell → etc.
  • Inner context — the content area inside the dashboard shell. Shows Overview → Manage Users → Settings etc., while the sidebar stays visible.

Each context has its own NavigationStore (its own back-stack). Pressing Back inside the shell only unwinds the shell's history, not the outer window's history.

Outer context store
MainWindowViewModel — owns the window's ContentControl
↑ UseContext() pushes on top
Inner context store (Admin shell)
AdminDashboardViewModel — owns the shell's sub-page area
↑ UseContext() pushes on top (if another shell opens)
...another inner context if needed

How a shell registers its context:

// AdminDashboardViewModel.cs — called when the admin shell loads
public async Task OnNavigatedToAsync()
{
    // Registers a new inner context.
    // From now on, NavigateToAsync() changes ActiveSubPage, NOT CurrentViewModel.
    _navContext = _navigationService.UseContext(vm => ActiveSubPage = vm);

    // Now navigate within this inner context
    await _navigationService.NavigateToAsync<AdminOverviewViewModel>();
}

public Task OnNavigatedFromAsync()
{
    _navContext?.Dispose(); // ← pops this context off the stack
    return Task.CompletedTask;
}
Key insight: UseContext(vm => ActiveSubPage = vm) is a delegate (callback). The service stores it and calls it every time NavigateToAsync() is used. Because the admin shell is "on top" of the context stack, navigation affects its ActiveSubPage, not the outer window's CurrentViewModel.

How the stacks look after admin logs in:

Context stack (NavigationService._contextStack):
  TOP →  vm => ActiveSubPage = vm      ← admin shell's delegate
         vm => CurrentViewModel = vm   ← main window's delegate

Store stack (NavigationService._storeStack):
  TOP →  AdminShellStore  { current: AdminOverviewVM, history: [] }
         MainWindowStore  { current: AdminDashboardVM, history: [LoginVM] }

When the admin shell disposes (_navContext.Dispose()), both stacks shrink back to just the main window level.

3 NavigateToAsync — creating ViewModels via DI

ViewModels are never created with new. The service uses ActivatorUtilities.CreateInstance to resolve all dependencies from the DI container automatically:

// NavigationService.cs
public async Task NavigateToAsync<TViewModel>()
    where TViewModel : class, INavigatable
{
    // 1. Create the ViewModel — DI injects all its constructor parameters
    var vm = ActivatorUtilities.CreateInstance<TViewModel>(_serviceProvider);

    // 2. Tell the active store to switch
    await NavigateCoreAsync(vm, () => vm.OnNavigatedToAsync());
}
// NavigateCoreAsync — the shared logic for all navigation calls
private async Task NavigateCoreAsync<TViewModel>(
    TViewModel vm, Func<Task> onNavigatedTo, bool clearHistory = false)
{
    var currentStore = _storeStack.Peek(); // get the active context's store

    // Notify the current VM that it's leaving
    await currentStore.CurrentViewModel?.OnNavigatedFromAsync();

    // Switch (with or without clearing history)
    if (clearHistory)
        currentStore.ResetTo(vm);           // no back button
    else
        currentStore.CurrentViewModel = vm; // push old VM to history

    // Notify the new VM that it has arrived (load data here)
    await onNavigatedTo();
    CanGoBackChanged?.Invoke(); // update Back button state in UI
}

Navigation with a parameter:

// Caller — AdminOverviewViewModel.cs
await _navigationService.NavigateToAsync<SupervisorDashboardViewModel, int>(chosen.Id);

// The target ViewModel receives it in OnNavigatedToAsync
public async Task OnNavigatedToAsync(int supervisorId)
{
    _currentSupervisorId = supervisorId;
    await LoadSupervisorDataAsync(supervisorId); // loads data for THIS supervisor
}
OnNavigatedToAsync() is where ViewModels load their data. It's called after the VM is set as current, so the View is already rendered (with a loading state) while data fetches happen asynchronously.
4 How the View updates — ContentControl + DataTemplates

The View side is completely passive. MainWindow.xaml has a single ContentControl bound to CurrentViewModel:

<!-- MainWindow.xaml -->
<ContentControl Content="{Binding CurrentViewModel}"
                HorizontalContentAlignment="Stretch"
                VerticalContentAlignment="Stretch" />

WPF's ContentControl looks at the type of whatever object is in Content and searches for a matching DataTemplate. All the mappings live in ViewModelViewMap.xaml:

<!-- ViewModelViewMap.xaml — ViewModel → View mapping table -->
<DataTemplate DataType="{x:Type uservm:LoginViewModel}">
    <userv:LoginView />
</DataTemplate>

<DataTemplate DataType="{x:Type adminvm:AdminDashboardViewModel}">
    <adminv:AdminDashboardView />
</DataTemplate>

<DataTemplate DataType="{x:Type adminvm:AdminOverviewViewModel}">
    <adminv:AdminOverviewView />
</DataTemplate>
<!-- ...one entry per ViewModel/View pair -->

Why DataTemplates instead of if/else in code-behind?
Zero code-behind switch statements. Adding a new screen means adding two lines to ViewModelViewMap.xaml. The rest is automatic. This also means WPF creates the View fresh every time, so there's no stale state in the UI.

The same pattern for the shell's sub-pages:

<!-- AdminDashboardView.xaml — inner content area -->
<ContentControl Content="{Binding ActiveSubPage}" />

When ActiveSubPage changes (set by the inner context's delegate), WPF again looks up the DataTemplate for that ViewModel type and renders the correct sub-page view.

5 INavigatable — the lifecycle contract

Every ViewModel that can be navigated to implements INavigatable. It provides two lifecycle hooks:

// INavigatable.cs
public interface INavigatable
{
    // Called AFTER this VM becomes current → load your data here
    Task OnNavigatedToAsync() => Task.CompletedTask;

    // Called BEFORE this VM stops being current → cleanup, stop timers
    Task OnNavigatedFromAsync() => Task.CompletedTask;
}

// Variant that accepts a parameter (e.g. which supervisor to show)
public interface INavigatable<TParameter> : INavigatable
{
    Task OnNavigatedToAsync(TParameter parameter);
}

Both methods have default implementations (do nothing), so a ViewModel only overrides what it needs.

Real examples:

// SupervisorDashboardViewModel — loads data when navigated to
public async Task OnNavigatedToAsync(int supervisorId)
{
    await LoadMatchingSettingsAsync();   // sets IsPhase1Active first (no flicker)
    await LoadSupervisorDataAsync(supervisorId);
    _ticker.Start();                     // start the countdown timer
}

public Task OnNavigatedFromAsync()
{
    _ticker.Stop();  // stop timer when leaving this page
    return Task.CompletedTask;
}

// AdminDashboardViewModel — shell opens/closes an inner context
public async Task OnNavigatedToAsync()
{
    _navContext = _navigationService.UseContext(vm => ActiveSubPage = vm);
    await _navigationService.NavigateToAsync<AdminOverviewViewModel>();
}
public Task OnNavigatedFromAsync()
{
    _navContext?.Dispose();  // collapse the inner context when shell leaves
    return Task.CompletedTask;
}
📖 Complete walkthrough — Admin logs in and inspects a supervisor
  1. App starts → MainWindowViewModel calls UseContext(vm => CurrentViewModel = vm) → registers the outer context, outer store is now active.
  2. App navigates to LoginViewModel → outer store's CurrentViewModel = LoginVM → event fires → delegate sets CurrentViewModel → WPF renders LoginView.
  3. Admin enters credentials → service calls NavigateToAsync<AdminDashboardViewModel>() → LoginVM pushed to history, AdminDashboardVM becomes current → AdminDashboardView renders.
  4. AdminDashboardViewModel.OnNavigatedToAsync() runs → calls UseContext(vm => ActiveSubPage = vm) → a second (inner) store is pushed on top of the context stack.
  5. Inside OnNavigatedToAsync() → calls NavigateToAsync<AdminOverviewViewModel>() → this now targets the inner store → ActiveSubPage = AdminOverviewVM → the shell's ContentControl renders AdminOverviewView.
  6. Admin clicks "Inspect Supervisor" → calls NavigateToAsync<SupervisorDashboardViewModel, int>(supervisorId) → inner store pushes AdminOverviewVM to history, makes SupervisorDashboardVM current → renders SupervisorDashboardView.
  7. Admin presses Back → GoBackAsync() → calls OnNavigatedFromAsync() on SupervisorDashboardVM (stops ticker) → pops AdminOverviewVM from history → OnNavigatedToAsync() on AdminOverviewVM runs (refreshes data) → back to overview.
Context stack at step 5 (two levels active):
┌─────────────────────────────────────────────────────────────────────┐
│  OUTER store  ·  current: AdminDashboardVM  ·  history: [LoginVM]   │
├─────────────────────────────────────────────────────────────────────┤
│  INNER store  ·  current: AdminOverviewVM   ·  history: []          │ ← active
└─────────────────────────────────────────────────────────────────────┘
  GoBackAsync() and NavigateToAsync() always target the TOP store.
📋 Quick reference — which method to call?
Method When to use Back button?
NavigateToAsync<VM>() Go deeper — user can press Back to return ✅ Yes
NavigateToAsync<VM,P>(param) Go deeper, passing a parameter (e.g. an ID) ✅ Yes
NavigateToRootAsync<VM>() Switch root section (sidebar navigation) — clears history ❌ No
NavigateToRootAsync<VM,P>(param) Root switch with parameter — clears history ❌ No
GoBackAsync() Return to the previous page in the current context — (is the back action)
UseContext(delegate) Shell ViewModels only — opens a new independent navigation zone Depends on inner history
Common mistake: Navigating to a shell ViewModel (like AdminDashboardViewModel) instead of a sub-page ViewModel creates a new nested shell — and a new sidebar. Always navigate to the sub-page ViewModel (AdminOverviewViewModel) when you want to go to a specific page inside a shell that's already open.
