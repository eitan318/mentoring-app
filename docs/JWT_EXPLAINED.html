🔐 How JWT Authentication Works

MentoringApp — full walkthrough from login to every API request

💡 What is JWT and why do we use it?

JWT (JSON Web Token) is a compact, self-contained token that proves who you are on every API call. Instead of the server keeping a "session table" of logged-in users, it hands you a signed token at login — and you present that token on every subsequent request.

The server can verify it without any database lookup, because the token carries the identity inside it, signed with a secret key.

Why JWT in this project?
Our API is stateless — it does not remember you between requests. Any request that arrives with a valid JWT is trusted, regardless of which server instance handles it. This makes the system easy to scale.

🧩 Anatomy of a JWT Token

A JWT is three Base64Url-encoded JSON objects joined by dots:

HEADER
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
PAYLOAD (claims)
eyJzdWIiOiI0MiIsIm5hbWUiOiJBbGljZSIsInJvbGUiOiJTdHVkZW50IiwibGFuZ3VhZ2UiOiJlbiIsImp0aSI6ImFiY2QiLCJleHAiOjE3MDAwMDAwMDB9
.
SIGNATURE (HMAC-SHA256)
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Header

Declares the algorithm used to sign the token:

{ "alg": "HS256", "typ": "JWT" }

Payload — the Claims

The payload carries claims — facts about the user. These are the exact claims our JwtHelper.cs puts in every token:

Claim keyValue exampleWhat it means
sub42User's database ID (Subject)
name"Alice Cohen"Display name
role"Student"Admin / Supervisor / Student — drives authorization policies
language"he"UI language preference, read on the client side
jti"a4b2c..."Unique token ID (prevents replay if you later build a blacklist)
exp1700000000Expiry timestamp (UTC Unix time)

Signature

HMAC_SHA256( base64(header) + "." + base64(payload), secretKey )

If anyone tampers with the header or payload — even one character — the signature no longer matches and the server rejects the token.

Important: The payload is Base64-encoded, not encrypted. Anyone can decode and read it. Never put passwords or sensitive data in a JWT payload.
1 Step 1 — Login: the two-step verification flow

Our login is a two-step email-verification flow. The client never sends a password — only a 6-digit code sent by email.

1a — Send verification code

// AuthEndpoints.cs
app.MapPost("/api/auth/send-code", async (SendCodeRequest request, AuthService authService, ...) =>
{
    // AuthService generates a 6-digit code, saves it to DB, emails it to the user
    var result = await authService.SendVerificationCodeAsync(request.NationalId, ...);
    return Results.Ok(...);
})
.AllowAnonymous();   // ← no JWT needed yet, anyone can call this

1b — Submit the code → receive JWT

// AuthEndpoints.cs
app.MapPost("/api/auth/login", async (LoginRequest request, AuthService authService,
                                          IOptions<JwtSettings> jwtOptions) =>
{
    // Verify the 6-digit code (expires after 10 minutes)
    var codeResult = await authService.VerificationCodeValid(request.Password);
    if (!codeResult.Success) return Results.Unauthorized();

    // Load the full user from DB
    var loginResult = await authService.LoginAsync(request.NationalId);
    if (!loginResult.Success) return Results.Unauthorized();

    // Build and sign the JWT
    var (token, expiresAt) = JwtHelper.GenerateToken(loginResult.Data!, jwtOptions.Value);

    return Results.Ok(new { token, expiresAt });   // ← sent back to client
})
.AllowAnonymous();

JwtHelper — building the token

// JwtHelper.cs
var claims = new[]
{
    new Claim(JwtRegisteredClaimNames.Sub,  user.Id.ToString()),
    new Claim(JwtRegisteredClaimNames.Name, user.UserName),
    new Claim("role",     role),          // "Admin" | "Supervisor" | "Student"
    new Claim("language", user.Language),
    new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString())
};

var key   = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(settings.Secret));
var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

var token = new JwtSecurityToken(
    issuer:            settings.Issuer,
    audience:          settings.Audience,
    claims:            claims,
    expires:           DateTime.UtcNow.AddHours(settings.ExpiryHours),
    signingCredentials: creds
);

return (new JwtSecurityTokenHandler().WriteToken(token), expiresAt);
After this call the client holds a token string like:
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJTdHVkZW50IiwiZXhwIjoxNzAwMDAwfQ.abc123...
2 Step 2 — Client stores the token in AuthTokenStore

The client (WPF / Blazor) receives the token and stores it in a singleton AuthTokenStore. This is an in-memory object — the token is never written to disk.

// AuthTokenStore.cs — singleton, lives for the entire app lifetime
public class AuthTokenStore
{
    public string?  Token    { get; set; }   // the JWT string
    public int?     UserId   { get; set; }   // parsed from the sub claim
    public string?  Role     { get; set; }   // "Admin" | "Supervisor" | "Student"
    public string?  Language { get; set; }

    public bool IsAuthenticated => Token != null;

    public event Action? SessionExpired;   // fires when API returns 401
}
The Role and UserId stored here are used directly by the client to decide which dashboard to show — without an extra API call.
3 Step 3 — Every API request carries the token (BearerTokenHandler)

A DelegatingHandler is a middleware in the HttpClient pipeline. It runs automatically before every outgoing HTTP request. Ours injects the Authorization: Bearer <token> header:

// BearerTokenHandler.cs
public class BearerTokenHandler(AuthTokenStore authTokenStore) : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        // Attach token to EVERY outgoing request automatically
        if (authTokenStore.Token != null)
            request.Headers.Authorization =
                new AuthenticationHeaderValue("Bearer", authTokenStore.Token);

        var response = await base.SendAsync(request, ct);

        // If the server says 401 (token expired / revoked) → notify the app
        if (response.StatusCode == HttpStatusCode.Unauthorized && wasAuthenticated)
            authTokenStore.NotifySessionExpired();   // ← navigates back to login

        return response;
    }
}
The developer does not manually add the header in each API call — the handler does it for every single request in the background.

The resulting HTTP request looks like:

GET /api/users/42 HTTP/1.1
Host: localhost:5000
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIs...
4 Step 4 — Server validates the token on every request

The API is configured with AddJwtBearer in Program.cs. It automatically intercepts every incoming request, reads the Authorization header, and validates the token before the endpoint code ever runs:

// Program.cs
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer           = true,   // must match settings.Issuer
            ValidateAudience         = true,   // must match settings.Audience
            ValidateLifetime         = true,   // rejects expired tokens
            ValidateIssuerSigningKey = true,   // signature must match the secret
            ValidIssuer    = jwtSettings.Issuer,
            ValidAudience  = jwtSettings.Audience,
            IssuerSigningKey = new SymmetricSecurityKey(
                                Encoding.UTF8.GetBytes(jwtSettings.Secret))
        };
    });

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("AdminOnly",         policy => policy.RequireRole("Admin"));
    options.AddPolicy("AdminOrSupervisor", policy => policy.RequireRole("Admin", "Supervisor"));
});

What is validated?

CheckWhat happens if it fails
Signature401 Unauthorized — token was tampered with
Expiry (exp)401 Unauthorized — token has expired
Issuer / Audience401 Unauthorized — token from wrong source
Role policy (AdminOnly)403 Forbidden — authenticated but not authorized

How endpoints use it

// UserEndpoints.cs — only Admins can call this endpoint
group.MapGet("/", async (UserService userService) => { ... })
     .RequireAuthorization("AdminOnly");

// RequireAuthorization() with no argument = any valid JWT (any role)
group.MapGet("/{id:int}", async (int id, UserService userService) => { ... })
     .RequireAuthorization();
5 Step 5 — Handling token expiry (session expired)

When a token expires, the server returns 401 Unauthorized. The BearerTokenHandler detects this and fires the SessionExpired event on AuthTokenStore:

// BearerTokenHandler.cs — triggered on 401
if (response.StatusCode == HttpStatusCode.Unauthorized && wasAuthenticated)
    authTokenStore.NotifySessionExpired();

// AuthTokenStore.cs — clears everything and raises the event
internal void NotifySessionExpired()
{
    if (_sessionExpiredNotified) return;  // fire only once even with concurrent requests
    _sessionExpiredNotified = true;
    Clear();                             // wipe Token, UserId, Role, Language
    SessionExpired?.Invoke();            // ← app navigates back to login screen
}
The _sessionExpiredNotified flag prevents multiple simultaneous API requests (all returning 401) from each triggering a separate navigation event.
📋 Complete Flow — Summary
  1. User enters their National ID → client calls POST /api/auth/send-code
  2. Server generates a 6-digit code, saves it to DB, emails it to the user
  3. User enters the code → client calls POST /api/auth/login with NationalId + code
  4. Server validates the code (10-minute expiry), then calls JwtHelper.GenerateToken
  5. Token (with sub, name, role, language, jti, exp) is signed with HMAC-SHA256 using the server's secret key
  6. Token string is returned to the client → stored in AuthTokenStore (in memory only)
  7. BearerTokenHandler automatically adds Authorization: Bearer <token> to every outgoing HTTP request
  8. Server receives request → AddJwtBearer middleware validates signature, expiry, issuer, audience → populates HttpContext.User with the claims
  9. Endpoint checks .RequireAuthorization("AdminOnly") etc. → 403 if role doesn't match, or proceeds
  10. If token has expired → server returns 401 → BearerTokenHandler fires SessionExpired → app returns to login screen
Key design benefit: The server is completely stateless — it stores no session data. Every piece of identity information (who you are, your role, your language) travels inside the token itself. Any server instance can validate any request without shared state.
⚙ Configuration — JwtSettings (appsettings.json)

All JWT parameters come from appsettings.json (base values) overridden by appsettings.Development.json:

// appsettings.json
{
  "JwtSettings": {
    "Issuer":     "MentoringApp.Api",
    "Audience":   "MentoringApp.Client",
    "ExpiryHours": 72
  }
}

// appsettings.Development.json (secret only here, never in production)
{
  "JwtSettings": {
    "Secret": "dev-secret-key-at-least-32-characters-long"
  }
}
SettingPurpose
IssuerWho created the token — validated on every request
AudienceWho the token is for — validated on every request
ExpiryHoursHow long the token is valid (72 h = 3 days)
SecretThe HMAC signing key — must be ≥ 32 characters; never commit to public repos
